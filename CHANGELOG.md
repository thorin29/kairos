## 0.312.0
- Fixes a real gap in the 0.311 offline-sync work: when an item created offline finally syncs, its temporary id is now rewritten to the server's real id *in the saved queue itself*, not just in memory for that one sync attempt. Before this, if the connection dropped between the create landing and a follow-up change (move/edit/complete) replaying, that follow-up could be sent under the old temporary id, rejected, and lost. The fix now survives a dropped connection, an app restart, or a reboot. Also wires the offline-queue unit tests into CI so this can't silently regress. App-only; cumulative (0.305-0.312).
## 0.311.0
- Final offline-sync hardening. Adding something offline and then changing, moving, completing, or deleting it before you reconnect now works correctly. Each created item carries a durable client id, so the queued create and the follow-up actions that reference it are properly linked: when the create finally syncs and the server assigns a real id, the queued follow-ups are rewritten to that id before they replay, and an add-then-delete done entirely offline cancels out to nothing. That same client id also gives an offline-created item one stable id across an app restart (previously it could be rebuilt under a different id). No visible change when you're online — this only affects the offline-then-reconnect path. Includes deterministic tests for the queue logic. Cumulative (0.305-0.311).
## 0.310.0
- Completes the offline temp-id fix from 0.309, now that the server returns the id of anything you create. Adding a book, grocery, money entry, task, or school assignment while online swaps the temporary id for the real one the moment the server confirms — before the follow-up refresh — so any next action (edit, delete, move) always targets the id the server knows. If that refresh then fails, the item stays on screen and is saved to the on-device cache with its real id. Against an older server that doesn't return ids yet, an unconfirmed new item is dropped from screen and cache until the next successful load brings it back with its real id, so it can never be acted on in a broken state. School also gains the keep-on-refresh-failure behavior the other screens got in 0.306. Also hardens offline delete: deleting a just-created item with nothing queued to cancel now surfaces as an offline failure to retry, instead of silently succeeding. Cumulative (0.305-0.310). ## 0.126.0
- Offline queue hardening (from a security review):
  - A queued offline write now stores a server-relative path and is always replayed
    against the server you're currently signed into — it can never be sent to a stale
    or different host.
  - Your device token is only ever attached to requests going to your configured
    server (API, sync, and avatar image loading), never to any other origin.
  - The queue is cleared automatically on sign-out, re-enrollment, a server change, or
    an expired login, so one person's pending writes can never replay under another.
  - Replaying a write is smarter about failures: temporary problems (auth, timeout,
    rate-limit, server errors) are retried; only writes the server flatly rejects are
    dropped, and those are now logged/counted instead of vanishing silently.
  - The offline queue is capped so a long outage can't grow it without bound.
